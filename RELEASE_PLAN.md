## Baseline implementation

| Area | State | Evidence and release consequences |
| --- | --- | --- |
| Native, local-first app | Implemented | SwiftUI app starts at ContentView. No accounts, backend, notifications, analytics, third-party dependencies or purchase code found. |
| Field and creation | Partial | Field shows full-width Do/Avoid bars and a visible Add button. Creation accepts title and type, appends to the store and returns to the Field. Input is only checked for blank spaces and saved untrimmed. The empty state advertises a pull-up that the Field does not implement. |
| Daily semantics | Model only | The stored flag means **done** for Do and **violation** for Avoid. The model toggles the flag, but the row never calls it or renders status. Missing or unmarked Do is neutral. Missing or unmarked Avoid is successful by default during its lifetime, while an explicit mark is a violation. Avoid defaults describe the rule, not a recorded check-in. Reversing either mark must preserve the day's note and number. |
| Navigation and display | Partial | Add and Close are wired. Field receives filter callbacks but attaches no swipe recognizers. There is no horizontal display toggle. The row receives badge and count inputs but renders neither. The Create screen replaces the Field and holds its draft locally. Switching to Timeline through a size-class change removes the form from the hierarchy and risks losing its draft. |
| Timeline | Partial | Compact vertical size class selects a read-only vertical list of marked dates, including Avoid violations without a distinct visual meaning. It omits unmarked notes and counts, expected defaults, and a shared day axis. Regular-height iPad landscape has no route to it. |
| Inspection and editing | Absent in UI | No long press, inspect action, rename, or day-entry editor. Optional notes and integer values exist in Codable models. The model's full entry replacement creates a new entry identity. Type is immutable, which preserves the meaning of historical marks. |
| Persistence | Partial | Synchronous JSON snapshots in bundle-specific Application Support, atomic primary write, and a previous-primary copy. Missing primary skips recovery. Any read or decode failure is treated as corruption and can start an empty store. The backup is never loaded. Backup replacement removes the prior copy first and may copy an invalid primary over the last good snapshot. Directory, quarantine and write failures are suppressed or logged. A mutation can appear saved and disappear on relaunch. There is no explicit storage version, upgrade fixture, recovery UI or guarantee across a schema change. |
| Civil dates | Fragile | Day keys use absolute Date values at Calendar.current midnight. Same civil day lookup can miss after timezone or calendar changes. No explicit today refresh exists at midnight or foregrounding. Define stable recorded day identity and deterministic legacy migration before creating more history. Old timestamps lack their original timezone, so document the migration assumption and keep the original bytes. |
| Color, cycling and retirement | Model fragments only | Do cycles and Avoid progression/retirement helpers exist, while their interactions and visual overlays do not. Avoid progression also treats negative elapsed days as overgrown. These fragments predate product discovery and do not establish the v1.0 rules. |
| Accessibility and layout | Partial | Standard Add, Close and form controls exist. Static bars have no actionable accessibility semantics or status values. Fixed total-height division can produce tiny rows, clips long or large text and provides no scrolling escape. The bottom button uses a fixed white background. Verify Dynamic Type, VoiceOver, Voice Control, contrast, 44-point targets, dark mode, reduced motion and iPad resizing before listing support. |

## Proposed v1.0 scope and purchase boundary

Keep the full-width Field as the main surface, inline creation, tap to mark, long press to inspect, and rotation as an optional shortcut to a compact, read-only day-aligned Timeline. Include visible equivalents for core gestures. Allow item rename and correction of daily status, optional notes and optional signed integer values. Keep type immutable. Include a manual archive with history retained and a way to reactivate. Ship reviewed color progression, degradation, recovery, and maturation as core behavior. Keep the relationship between maturation and archive/reactivation open during discovery. Add a visible All/Do/Avoid filter if needed for clear navigation. A flexible Field with minimum row sizes and scrolling should retain the existing design at low item counts.

- **Free forever** includes every core workflow above for up to three active items in any Do/Avoid mix. Full history and previously recorded data remain available at every tier. Archiving frees a slot. Users with more than three existing active items retain access and can continue tracking them. The limit applies to creating or reactivating more items. The Field and recovery remain usable offline.
- **One-time unlock** removes the active-item limit permanently for the v1.0 feature grant. State the limit and included purchase benefit before purchase and on the store listing. The three-item cap and paid benefit require developer approval before purchase implementation.
- **Later** includes optional numeric display layers, richer gestures, aggregates, optional export, and any lifecycle automation outside the approved progression behavior. Defer subscriptions and subscription UI. Keep accounts, backend, reminders and analytics outside v1.0.

Use one non-consumable StoreKit 2 product. Map its product identifier to a durable v1 capability, independent of items, JSON and schema migrations. A future subscription can grant additional capabilities that union with permanent grants. Expiration, unknown purchase state and refunds must never mutate, hide or delete user data. Treat pending, cancellation, unavailable StoreKit and unverified results distinctly. Load verified current entitlements on launch, listen for verified updates, apply grants before finishing transactions, and offer explicit Restore Purchases via `AppStore.sync()`. Prefer StoreKit's locally available verified history offline. Preserve the last verified permanent grant through transient failures, reconcile on a reliable refresh, and honor verified revocations or refunds without changing saved records. Never use a writable local Boolean as purchase authority, or promise restoration of local entries on reinstall via StoreKit. [Apple transaction verification](https://developer.apple.com/documentation/storekit/transaction) · [Apple restore guidance](https://developer.apple.com/documentation/storekit/appstore/sync())

## P0.2 data contract and P0.3 entry

Storage v1 retains item and entry IDs, creation instant and day, item kind, archive flag, and each recorded day's mark, note and integer value. Days are Gregorian date labels. “Today” follows the device's time zone. Existing labels stay fixed when the device travels or changes calendars. The legacy format retained instants at local midnight without their original time zone. Migration uses the device's time zone at first load, saves the exact legacy bytes, and blocks writes if two records collapse into the same day. A record originally created in another time zone can be assigned to a neighboring day during migration.

Versioned snapshots are written atomically. Updates keep the previous valid primary as a backup and publish changes only after the new primary writes successfully. A valid backup can replace a malformed or missing primary. Recovery is visible, and recoverable corrupt bytes are retained. An unknown version, ambiguous migration, unreadable file, or absence of a valid snapshot when there is evidence of prior history stops normal editing and offers a load retry.

P0.3 can start once simulator tests pass, an actual install over the pushed baseline migrates a representative fixture and preserves it through relaunch, and the unchanged app identity and Release build are verified. Use the committed storage API, civil-day keys, and status resolution as the starting point. Approval of a progression formula, palette or paid boundary is not an input to the experiment.

### P0.2 verification

Xcode 26.2 passed all 17 tests on iPhone 17 Pro with iOS 26.2. The unsigned generic iOS Release build passed. On a fresh simulator, baseline build 1 from `924a76d` was installed and launched with a [fixture encoded by the baseline models](DoAvoidTests/legacy-history.json). The in-place upgrade to build 2 preserved both items, all entry IDs and payloads, archive state, and exact source bytes. Relaunch left the migrated snapshot unchanged. Injected corruption restored the backup with a visible notice. Corrupting both snapshots showed the unavailable-history screen and preserved both files.

Run [the simulator upgrade check](scripts/test-simulator-upgrade.sh) with the baseline and upgrade simulator app bundles and a directory for captures and logs. Build the baseline from `924a76d` and set `CURRENT_PROJECT_VERSION=2` when building the upgrade app for the test. The committed build setting stays at 1.

```sh
scripts/test-simulator-upgrade.sh /path/to/baseline/DoAvoid.app /path/to/upgrade/DoAvoid.app /tmp/doavoid-upgrade
```

The normal backup is a prior saved state, so recovery can omit changes newer than that snapshot. A first save on a new installation has no prior snapshot to rotate. Signed device and TestFlight upgrade checks remain in P0.4 and P0.5.

### P0.3a — Internal distribution and progression lab

Build a development-only progression environment in simulator and development builds. Reuse the real SwiftUI Field and Timeline components with the same parameterized progression logic used to project their examples. Inject the current day and simulated histories. Provide fast side-by-side or switchable comparisons of candidate parameters, visual mappings, and lifecycle behavior. Include controls and reproducible fixtures for:

- New items, sustained and intermittent Do completions, Avoid violations and recovery, and prolonged inactivity and re-engagement.
- The same history rendered on the Field and Timeline, with a scrubbed date, comparisons between candidates, and reviewable previews or simulator captures.
- Maturation and archive/reactivation candidates, default Avoid status without recorded events, past-day edits, and histories across time-zone and DST transitions.

Create examples in memory or a development-specific store with no path to the production writer. Keep scenario data and controls out of App Store builds through compile-time exclusion and verify the Release bundle. Tests should cover deterministic projections, parameter changes, historical edits, and data isolation. Record the reviewed scenarios and decisions before declaring the algorithm, color system, or visual design complete.

Progression should derive from recorded day labels, item type, creation day, explicit marks, and an injected evaluation day. Preserve the distinction between an implicit Avoid success and a recorded event. The current archive flag captures the latest state. If review calls for reconstructing exact maturation, pause periods, or reactivation dates, those would require explicit lifecycle events or an additive schema change. Do not infer historical archive dates from blank days or store any experimental score as canonical history.
